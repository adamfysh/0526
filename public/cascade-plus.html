Eight corridors now, click any vessel for its route/cargo/ETA. Five real-routing corridors, each computed live by narrows-routing-api against a real representative voyage: Bab el-Mandeb (→ Cape of Good Hope), Suez (its own scenario — a Suez-specific closure with Bab still open, not the same trigger as Bab's own row above, computed separately), Malacca (→ Sunda Strait, the graph has no separate Lombok tag), Panama (→ whichever the engine finds shorter for that voyage), and Gibraltar (→ the only way into the Mediterranean from the Atlantic; closing it forces the full way around via the Cape, Bab, and Suez). Three terminal-strait corridors have no alternate route to compute and are costed as flat, labeled estimates: Hormuz, Bosphorus, and Danish Straits.

Stopped at 8, not 15-20, for an honest reason. Several more chokepoints Narrows already tracks elsewhere (Dover/English Channel, Kiel Canal, Mozambique Channel, Luzon Strait, St. Lawrence) do have real alternatives in the physical world, but narrows-routing-api's graph has no passage tag for any of them yet, so I can't compute a real number for them the way I can for the five above. Labeling them "terminal, no alternative" the way Hormuz is would be wrong, since they're not terminal, the data just isn't there yet. Adding those tags to the graph is real engineering on the routing side, not something to fake on this page. Dardanelles was deliberately left out of the terminal set too, since it's the same physical exit as Bosphorus (a Black Sea vessel needs both to leave), not a second independent chokepoint.

Origins are real ports, not basins. Every corridor's from/to endpoint is a named port with real coordinates from the Narrows port index (World Port Index-derived, ~4,000 ports), not a basin-level approximation — Al Fujayrah, Jiddah, Singapore (Keppel), Houston, New York, Ras Tannurah, Novorossiysk, Primorsk, Rotterdam, Shanghai, Genova. This is the same data a future map layer would need, so fixing it here first means the route math, the labels, and any eventual map all agree on where these voyages actually start and end.

Status is computed, not authored. Locked/window/pre used to be assigned by hand per vessel. They're now derived every render from each vessel's ETA against the scenario clock in the header — move the clock forward and vessels migrate buckets on their own, the way real risk would. Diversion days are now per-vessel too: class and CII grade set an effective speed (the same "CII-adjusted effective days" idea Narrows' own Malacca/Lombok analysis already publishes), not one flat speed for every ship.

Diverting doesn't mean safe. When a vessel diverts out of a real corridor, its actual computed alt-route is checked against every other tracked corridor's own passage signature — Panama's alt-route already runs through Suez and Bab el-Mandeb; Gibraltar's through the Cape, Bab, and Suez. If it matches, the vessel gets a second, linked row in that corridor tagged "displaced from X," with its value-at-risk moved there, not duplicated. This is the actual mechanism the name CASCADE+ refers to.

Built to receive shared assumptions later, not fake them now. Corridors, JWC flags, and per-class speed live in one clearly marked block in this file, the same shape NARROWS-RATES.js already uses as a real shared file across CAPE and CASCADE+ — the next step is making corridors/JWC/speed a shared file the same way, so this page and CAPE/CDM stop hand-copying each other. Separately: JWC war-risk polygons newly enclosing a port should move that port's PRI score, but that's a geospatial join that belongs in the pipeline, not this page — there's a named, empty PRI_JWC_OVERLAY object in the code marking exactly where that feed plugs in once it exists.
